Artifact description

The artifact is the same Inventory Management Android application created in CS 360. Before this enhancement, inventory records were displayed in a basic grid with no substantial searching, filtering, sorting, or analytics. I selected the application because inventory management creates a practical context for comparing algorithms and data structures rather than demonstrating them in isolation.

Why this artifact belongs in my ePortfolio

The enhancement shows my ability to design and evaluate computing solutions using algorithmic principles. The completed application does more than present stored data: it helps users locate records, prioritize low-stock items, sort information, and understand inventory status. These features are valuable to an IT Administrator or system operator who must quickly interpret operational data and make informed decisions.

Enhancement and skills demonstrated

I separated the full inventory collection from the filtered and sorted collection displayed by the RecyclerView. A reusable InventoryAlgorithms class now contains indexing, filtering, sorting, and analytics logic, keeping algorithm behavior independent from Android interface code.

The application builds a normalized SKU HashMap in O(n) time after loading inventory. Exact SKU queries then use average O(1) lookup, trading a modest amount of additional memory for faster retrieval. When a query is not an exact SKU, a single-pass O(n) filter performs case-insensitive partial matching against names and SKUs while optionally enforcing the low-stock condition.

I implemented a custom stable merge sort with O(n log n) time complexity and O(n) auxiliary space. Comparator strategies support alphabetical order, ascending and descending quantity, and low-stock-first ordering. The stable merge behavior preserves the relative order of records considered equal, making results predictable. Inventory statistics are computed in one O(n) traversal and include distinct-item count, total quantity, low-stock count, and the item with the lowest quantity.

Trade-off: the HashMap consumes additional memory, but it avoids scanning the full collection for exact SKU searches. Merge sort also requires auxiliary storage, but it provides reliable O(n log n) performance and stable ordering.

Testing and quality

Focused JUnit tests verify exact and missing SKU lookups, partial-name and partial-SKU filtering, low-stock filtering, all sorting modes, and inventory-statistics calculations. Reapplying the algorithms after additions, deletions, and quantity changes keeps the visible results and analytics synchronized with the source data.

  • Computing practices: reusable algorithm code, responsive UI integration, and automated tests deliver practical value.
  • Professional communication: code comments, test names, and the narrative explain both behavior and complexity to technical and nontechnical audiences.

Reflection

This enhancement reinforced the difference between functionality and efficiency. A linear scan is appropriate for flexible partial matching, while a HashMap is better for exact keyed lookup. I learned that no single structure is ideal for every query and that a professional solution can combine strategies based on expected use.

The main challenge was integrating new processing behavior without breaking quantity updates, low-stock alerts, database reloads, or RecyclerView state. Keeping the algorithms in a dedicated class made the work easier to test and reason about. I also encountered configuration and hidden-file build issues while setting up unit tests; resolving them strengthened my understanding of project structure and repeatable testing.

No specific instructor feedback changed the planned outcome coverage. The implementation followed the Module One plan while adding stronger evidence through complexity documentation, an exact-SKU index, analytics, and automated tests.
